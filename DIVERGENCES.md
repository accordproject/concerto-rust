| DV-009 | engine | `new Date(string)` falls back to V8's legacy date parser for any string outside the ECMAScript date time string format, and it accepts many more forms (`Nov 28 2022`, `28 Nov 2022 10:00 GMT+1`, ...). dayjs reaches it for a non-strict `DateTime` value (`strictQualifiedDateTimes: false`), a string default value and `dayjs.utc(string)` in general. | The Rust port parses the ECMAScript format with the V8 extensions the corpus reaches (any number of fraction digits, `24:00`, a space or lower-case `t` separator, a lower-case `z`, a `±HHmm` offset) and, from the legacy parser, a date of two or three numbers alone (`MM-DD`, `--MM-DD`, `MM/DD/YYYY`, `YYYY/MM/DD`, V8's default year 2001). Any other legacy form is an invalid date in Rust. So is a string with an embedded NUL (U+0000): V8's date tokenizer reads U+0000 as the end of its input, so `new Date('1970-01-01T00:00:00.000+00:00\u0000')` (and anything after the NUL, e.g. `...\u0000junk`) parses as the prefix, while the Rust parser, which matches the whole string, rejects it (found by P5-05 differential fuzzing, accordproject/concerto-rust#76: `Serializer.fromJSON` seed `data/Serializer.fromJSON/024a285d00093fff73ca0e8d.json`, mutationSeed 3124886527, `t: "1970-01-01T00:00:00.000+00:00\u0000"`; plan-owner confirmation tracked in accordproject/concerto-rust#169). | DV-013 | ts-bug | `ClassDeclaration.getProperties`, `getProperty` and `getIdentifierFieldName` recurse into the super type with no cycle check, so a cyclic inheritance chain (`A extends C`, `B extends A`, `C extends B`) makes `validateModelFiles`/`addCTOModel` fail with V8's `RangeError: Maximum call stack size exceeded` (PORTING.md 2.5). Ported as TS has it: the Rust walk is a loop with a visited set, and on a cycle returns `ErrorKind::JsRangeError` with that message (`engine-rangeerror-maxcallstack`, location `None`) instead of overflowing the native stack or reporting a cycle. `ModelManager.isAssignableTo` and `ClassDeclaration.getAllSuperTypeDeclarations` (`is_assignable_to`, `get_all_super_type_names`) reach the same cycle too: `getAllSuperTypeDeclarations` walks the chain iteratively rather than recursively, so on a cyclic chain it does not overflow the call stack — it loops until the process runs out of memory instead. `isAssignableTo` goes through `derivesFrom`, which walks `getSuperTypeDeclaration()` in its own iterative loop: on a cycle that contains the target it returns `true`, and on one that doesn't it loops until the process runs out of memory.
