# Divergences

Differences from the TypeScript reference that the port keeps on purpose. See
PORTING.md section 7.3 for the categories and the rules for adding a row.

| id | category | TS 5.0.0 behaviour | expected elsewhere (v4 spec / conformance / "correct") | evidence (fixture id, test title) | Rust site |
|----|----------|--------------------|---------------------------------------------------------|-----------------------------------|-----------|
| DV-001 | engine | TS has no serde step, so no counterpart for which malformed field a deserialisation error names. | With `preserve_order` (required by OD-3), a node with two or more malformed fields reports the first one in the node's own key order. Before P1-02 it reported them in alphabetical key order. No oracle outcome or conformance result changes (60 PASS on both). Accepted by the plan owner on #87. | The P1-02 review compared the base and new builds over 1,736 runs; the only 7 differences are this case (e.g. a class with a malformed `name` and `isAbstract`). | `concerto-core/Cargo.toml` (`serde_json` `preserve_order`) |
| DV-002 | ts-bug | `ModelUtil.isValidIdentifier(undefined)` and `(null)` return `true`: `ID_REGEX.test` converts its argument with `String()`, and `"undefined"` and `"null"` are valid identifiers. | An absent name is not a valid identifier. | `unit/ModelUtil.isValidIdentifier` fixtures with `{"@@oracle":"undefined"}` and `null` arguments (both `ok: true`). | `concerto-wasm/src/lib.rs` (`modelUtilIsValidIdentifier` applies `String()`); `concerto-core/src/model_util.rs` `is_valid_identifier`, test `id_regex_follows_the_ts_classes` |
| DV-003 | d6 | `ModelUtil.parseNamespace('org.acme')` accepts an unversioned namespace and returns `version: null`, `versionParsed: null`. | Namespace versions are mandatory in Concerto v4; the pre-port Rust `parse_namespace` rejected it. The loader keeps its own versioned check (`split_versioned_namespace`) until P2-08 ports `ModelFile`. | PORTING.md 3.6; `ModelUtil #parseNamespace` tests. | `concerto-core/src/model_util.rs` `parse_namespace` |
| DV-004 | engine | JS strings are UTF-16 and may hold a lone surrogate; the WASM boundary passes strings as UTF-8, so a lone surrogate reaches Rust as U+FFFD. No oracle outcome changes: no fixture or unit test passes one. For `isValidIdentifier` the verdict is the same either way (neither a lone surrogate nor U+FFFD is in an `ID_REGEX` class). | The same UTF-16 string on both sides. | None (no fixture observes it). | `concerto-wasm/src/lib.rs` (module docs) |
| DV-005 | engine | `JSON.stringify` prints an integral JS number without a fractional part or exponent below 1e21 (`5`, not `5.0`). | OD-3 widens the generated Integer and Long AST fields to `f64` so every JS number loads (accordproject/concerto-rust#90); serialising an `mm::*` value straight back to JSON now prints an integral bound as `5.0` (`serde_json`'s `f64` writer, via `ryu`), and a very large one as `1e19` rather than TS's `10000000000000000000`. No oracle or conformance outcome changes: nothing compares the typed re-serialization byte for byte today, and `ModelFile::ast()`/`getAst()` stay the source of truth for the AST text (OD-3, `preserve_order`), never the typed round trip. Flagged for whoever next serializes an `mm::*` number back out to text a TS caller reads (for example a WASM boundary echoing a validator back). | `concerto-metamodel/tests/numeric_widening.rs` (`a_widened_long_bound_round_trips_exactly`). | `concerto-metamodel/build.rs` (`generate_field`, `IntegerProperty`/`LongProperty` → `f64`) |
| DV-006 | ts-bug | `ResourceValidator.checkMapType` always asks `ModelUtil.isScalar(mapDeclaration.getKey())` to decide whether to unwrap a resolved key/value declaration to its scalar base type — even while checking the *value* slot, never `getValue()`. A map whose value type is a scalar is checked against the *key*'s scalar-ness instead. | A map's value slot should be unwrapped by the value type's own scalar-ness. | `instance::validate::tests` map fixtures exercise the primitive/enum/relationship paths this gate also guards; no fixture isolates a scalar-typed map *value* specifically, so this is ported by reading the TS source, not by an observed corpus divergence. | `concerto-core/src/instance/validate.rs` `map_key_is_scalar`, `check_map_type` |
| DV-007 | ts-bug | `ResourceValidator.checkMapType` resolves an `ObjectMapValueType`/`RelationshipMapValueType` value by looking up a declaration of that name and, if it is class-like, recursing with `visitClassDeclaration` — so a `RelationshipMapValueType` map value is validated as a nested embedded object (it must satisfy `obj instanceof Resource`), never as a relationship URI string the way a `RelationshipProperty` field is. | A map value declared as a relationship type would be expected to hold a relationship reference, the same as `RelationshipProperty` does. | `instance::validate::tests::a_map_with_a_relationship_typed_value_accepts_a_nested_resource`. | `concerto-core/src/instance/validate.rs` `check_map_type` |
